# ScubaMob Code Review

**Scope:** Full manual review of the Django backend (`scuba/*`), excluding test files and migrations (the custom apps currently have no migrations at all — schema is synced directly from models; this is a known, deliberate state, not a finding). Every non-test, non-migration `.py` file across all 19 apps, `scuba/settings.py`, `scuba/urls.py`, and `manage.py` was read in full.

**Method:** Three parallel reviews covering (1) `accounts` + `security`, (2) `divesites`, `galleries`, `sitesettings`, `diveshops`, `equipment`, `logbooks`, `divegroups`, and (3) `libs`, `aws`, `content`, `home`, `maps`, `robots`, `search`, `entities`, `environ`, `system`, `cache`, plus settings/urls. The two most severe findings (the auth backdoor and the `DEBUG`/`SECRET_KEY` defaults) were independently re-verified by reading the source directly.

**How to read this document:** findings are grouped by severity, then by file. Each entry states the concrete failure scenario (what input/state triggers what wrong behavior), not just a style preference.

---

## Executive Summary — fix these first

1. **Account-impersonation backdoor** in the login flow (`scuba/libs/authentication/adminoverride.py`) — anyone with one admin's credentials can log in as any other user.
2. **Unauthenticated arbitrary file write / disk-fill DoS** on a public webhook (`scuba/security/apis.py`).
3. **Unauthenticated stored XSS + disk-fill DoS** on public CI webhooks (`scuba/aws/apis.py`, rendered via `mark_safe()` in `scuba/aws/admin.py`).
4. **`DEBUG` defaults to `True`** and **`SECRET_KEY` silently falls back to a known insecure value** if the environment variable is missing (`scuba/settings.py`).
5. **The private-profile authorization gate doesn't check privacy at all** (`CanViewProfile` in `scuba/accounts/permissions.py`), and the views it's supposed to protect currently crash before that matters (`scuba/accounts/apis/profile.py`).
6. Several entire features are non-functional as shipped: **media/photo upload**, **dive log editing**, **email sending**, **image compression**, and the **main dive-site listing page** all throw unhandled exceptions on first use. These aren't edge cases — they're the primary code paths.
7. **`requirements.txt` is missing packages that are actively imported or invoked today** — `googlemaps`, `django-ses`, `requests`, and `flake8` are all used/run but not declared, meaning some of the failures above (email sending, Google address lookups) can't work in *any* environment, not just misconfigured ones.

Everything below is organized by severity so you can triage in order. `scuba/settings.py` and `requirements.txt` each have their own exhaustive dedicated sections (below the Executive Summary) since both were reviewed line-by-line on request — some items there are also referenced briefly in the severity sections that follow.

## scuba/settings.py — Complete Findings

This file (297 lines) was read in full, line by line, and every setting was cross-checked against how it's actually consumed elsewhere in the codebase (via grep/verification, not assumption). Findings below are exhaustive for this one file; a few are also mentioned briefly in the Critical/High/Medium sections further down because they affect app-wide behavior — this section is the authoritative, complete version.

### Critical

- **Lines 13, 45 — `DEBUG` defaults to `True`.** `env.Env(DEBUG=(bool, True), ...)` then `DEBUG = env("DEBUG")`. Any deployment that forgets to set the env var explicitly runs with debug mode on: full stack traces, settings values, and SQL exposed to any visitor on an unhandled exception — and this review found several confirmed unhandled-exception paths reachable by anonymous users (e.g. `scuba/aws/apis.py`, `scuba/home/apis.py`). *Fix: default to `False`.*
- **Lines 14, 35 — `SECRET_KEY` silently falls back to a known, public string** (`"dev-only-insecure-secret-key"`) if `DJANGO_SECRET_KEY` is unset. This breaks the integrity of session signing, CSRF tokens, and password-reset tokens the moment it's ever hit in a real deployment. *Fix: use `environ.Env.NOTSET`/no default so a missing key fails startup loudly instead of degrading silently.*
- **Line 217 — `EMAIL_BACKEND = 'django_ses.SESBackend'`, but `django-ses` is not a declared dependency and is not installed.** Confirmed: `grep -i ses requirements.txt` finds nothing, and `pip show django-ses` in the project's own venv reports "Package(s) not found." Since Django imports `EMAIL_BACKEND` lazily on first use (not at process startup), this means **every single call to `send_mail()`/`get_connection()` in every environment** — confirmation codes, password resets, welcome emails, anything routed through `scuba/libs/mail.py` — raises `ModuleNotFoundError: No module named 'django_ses'` the first time it actually runs. This is more fundamental than the separately-found `store_email()` bug in `scuba/libs/mail.py` (that bug fires *after* a successful send; this one means the send can never succeed at all). *Fix: add `django-ses` to `requirements.txt` and install it, or switch to a backend that's actually available (e.g. `django.core.mail.backends.smtp.EmailBackend` or the console backend for non-prod).*
- **Operational/process gap — production settings appear to live entirely outside this repository, and it's unclear they're even wired up correctly.** `scripts/buildspec.yml` runs `aws s3 cp s3://scubamob-prod/system/settings.py /scuba/system/settings.py` during the build. Two things are worth flagging about this: (1) whatever production-specific overrides that file is meant to provide (`DEBUG`, `SECRET_KEY`, etc.) are not in version control, not code-reviewed, and not diffable — a real audit-trail gap for exactly the settings this review is most concerned about. (2) The destination path (`/scuba/system/settings.py`) is an **absolute filesystem path at the OS root**, not a path inside the checked-out repository, and `scuba/system/settings.py` does not exist anywhere in this repo (confirmed — only `admin.py`, `apps.py`, `__init__.py`, `models.py`, `urls.py` exist in `scuba/system/`). Django's active settings module is `scuba.settings` everywhere this could be checked (`manage.py`, `pytest.ini`), never `scuba.system.settings`. Based on what's visible in this repository, this S3-fetched file does not appear to be imported by Django at all — meaning production may simply be running on this file's own (insecure) defaults. **This is flagged as an open question for whoever manages the deployment, not a certainty** — there may be host-level configuration (a systemd env file, a different `DJANGO_SETTINGS_MODULE` override, a symlink) not visible from the repo that makes this work correctly. It's worth confirming explicitly given how much rides on it.

### High

- **Line 215 — `GALLERY_BUCKET = 'scubamob.gallery.dev'` is hardcoded with no environment-variable wiring at all**, unlike its siblings `AWS_S3_BUCKET`/`AWS_S3_BUCKET_PRIVATE` (both go through `env()`). Confirmed via grep that this constant is actively used for real S3 uploads and deletes (`scuba/galleries/models.py:97,137`, `scuba/galleries/signals.py:23-24`) — meaning every deployment, including production, stores and deletes real user photos in a bucket whose name literally says `.dev`, and there is no way to point a different environment at a different bucket without editing this source file.
- **Line 234 — `AWS_PROFILE = 'default'` is hardcoded and confirmed used** in `scuba/libs/aws/s3.py:28,49` to build `boto3.Session(profile_name=AWS_PROFILE)`. This requires a named AWS CLI profile called `"default"` (normally a `~/.aws/credentials` entry) to exist on whatever host runs this code. Production/CI environments typically authenticate via IAM instance roles or explicit environment credentials, not a named profile file — if no such profile exists on the deploy target, every S3 call (uploads, deletes, the gallery/content storage this whole app depends on) fails with `ProfileNotFound`. Also not environment-configurable.
- **Lines 209-211 — `FACEBOOK_APP`, `FACEBOOK_APP_ID`, `FACEBOOK_API_SECRET` are hardcoded to empty strings directly in source**, with no `env()` call wiring them up at all (contrast with `GOOGLE_API_KEY` a few lines away, which at least goes through `env()`). These can never be set via environment configuration without a code change — any Facebook-dependent feature is permanently non-functional regardless of deployment.
- **Line 256 — `VALID_CONTENT_TYPES` is declared but never referenced anywhere in the codebase** (confirmed via repo-wide grep — zero consumers). This reads like it was meant to be the server-side upload content-type allowlist, but nothing enforces it. Combined with the earlier finding that `scuba/galleries/models.py` trusts client-supplied `content_type` directly with no validation, this is a security control that exists in name only in settings but isn't wired to anything.
- **No `SESSION_COOKIE_SECURE`, `CSRF_COOKIE_SECURE`, `SECURE_SSL_REDIRECT`, `SECURE_HSTS_SECONDS`, or `SECURE_PROXY_SSL_HEADER` anywhere in the file** (confirmed via grep — none exist). Session and CSRF cookies can be sent over plain HTTP. Since `DEFAULT_AUTHENTICATION_CLASSES` in `REST_FRAMEWORK` includes `BasicAuthentication` (credentials sent on every request), the lack of any HTTPS-enforcement setting means Basic Auth credentials could be transmitted in cleartext.
- **No `ADMINS`, `MANAGERS`, or `SERVER_EMAIL` configured anywhere** (confirmed via grep). Django's built-in "email the admins on a 500 error" mechanism (`AdminEmailHandler`, wired to the `django.request` logger by Django's *default* logging config, which stays active here since `'disable_existing_loggers': False`) silently does nothing when `ADMINS` is empty. Combined with `DEBUG` defaulting to `True`, if that default is ever hit in production, the two failure modes compound: errors aren't hidden from users, and nobody gets notified either.
- **Lines 274-275 — `CORS_ORIGIN_ALLOW_ALL = True` / `CORS_ALLOW_ALL_ORIGINS = True`, but `django-cors-headers` is not a declared dependency** (confirmed absent from `requirements.txt`) and isn't in `INSTALLED_APPS`/`MIDDLEWARE`. Currently a no-op, but a landmine: the moment someone adds `corsheaders` to actually fix a CORS problem, the app will silently allow every origin, including credentialed requests, because this permissive setting is already sitting there.

### Medium

- **Lines 159-172 — `AUTH_PASSWORD_VALIDATORS` is fully configured** (similarity, minimum length, common-password, numeric validators) **but nothing in the actual signup/registration code calls Django's `validate_password()` function** — per the accounts review, three separate signup paths in this codebase each enforce their own inconsistent, weaker rules (as little as 4 characters) instead. This configured policy is a password policy that exists on paper but is never actually enforced on user signup.
- **Line 144 — `'PAGINATE_BY': 2` is not just a bad value, it's the wrong setting key entirely.** `PAGINATE_BY` was DRF's pre-3.0 pagination setting name; it has no effect at all on the installed DRF version. The real key is `PAGE_SIZE`, and pagination additionally requires `DEFAULT_PAGINATION_CLASS` to be set — neither is present. This means **no default pagination is actually configured**; every `ListAPIView` in the project returns its full queryset unless it sets its own `pagination_class` explicitly.
- **`rest_framework.authtoken`'s `TokenAuthentication` tokens never expire by default, and there is no `DEFAULT_THROTTLE_CLASSES`/`DEFAULT_THROTTLE_RATES` anywhere in `REST_FRAMEWORK`.** A leaked/stolen token is valid indefinitely, and no endpoint in the project is rate-limited — this compounds the separately-found brute-forceable 6-digit signup confirmation code.
- **Line 121 — `'rest_framework.authentication.TokenAuthentication'` is appended to `AUTHENTICATION_BACKENDS`**, which is Django's *auth-backend* list, not a DRF authentication-class list. DRF's `TokenAuthentication.authenticate(self, request)` has an incompatible signature for Django's `authenticate(request, **credentials)`, so Django's `authenticate()` raises `TypeError` internally and silently skips it — this entry does nothing. The two backends listed after it (`AdminOverride`, `UsernameAuthentication`) are what's actually handling username/password login, and both have their own critical/high findings elsewhere in this document.
- **Lines 185-186 — `USE_TZ = False` with `TIME_ZONE = 'UTC'`.** With `USE_TZ = False`, `django.utils.timezone.now()` returns the naive *server local clock* time, not UTC — the `TIME_ZONE = 'UTC'` setting has essentially no effect on what gets stored in this mode. Every `auto_now_add`/`auto_now` timestamp in the entire schema is therefore timezone-ambiguous and depends entirely on whatever timezone the host OS happens to be set to, directly contradicting the project's own "use timezone-aware datetimes" rule.
- **Lines 194-196 — `STATICFILES_DIRS` includes the entire `node_modules` directory** as a static source. `collectstatic` walks every installed npm package (dev dependencies included, since there's no visible dev/prod split here) and makes its contents servable under `/static/` — this bloats build output and can expose npm package internals (source, license files, occasional test fixtures) that were never meant to be public web assets.
- **Line 239 — `FILE_UPLOAD_HANDLERS` is restricted to `[TemporaryFileUploadHandler]` only**, removing Django's default `MemoryFileUploadHandler`. Every uploaded file, however small, is now always written to a temp file on disk before processing. Not incorrect by itself, but it's an unexplained performance choice, and it isn't paired with any `FILE_UPLOAD_MAX_MEMORY_SIZE`/`DATA_UPLOAD_MAX_MEMORY_SIZE`/size cap — there is no project-wide ceiling on upload size at all, consistent with the separately-found lack of file-size validation in the `galleries` app itself.
- **Lines 133-138 — `DATABASES` has no `CONN_MAX_AGE` and no MySQL-specific `OPTIONS`** (e.g. `charset='utf8mb4'`). Given this is a social platform where dive-log notes, messages, and bios will plausibly contain emoji/4-byte Unicode, and MySQL's non-`utf8mb4` charsets silently mangle or reject those characters, this is a concrete data-integrity risk specific to the "MySQL is the production target" requirement — and it's invisible to the current test suite, since SQLite doesn't have this failure mode at all.
- **Lines 200-201, 218 — `EMAIL_FROM`, `EMAIL_BCC`, `DEFAULT_FROM_EMAIL` are hardcoded string literals**, not environment-configurable, so dev/staging can't use a different sending address than production. `EMAIL_BCC` is also set to the exact same `no-reply@scubamob.com` address as `EMAIL_FROM` — every outgoing email blind-copies an address that, by its own naming convention, is presumably unmonitored. Looks like a leftover placeholder or a broken attempt at an email archive.
- **Line 203 — `PRODUCTION_GALLERY_URL` is hardcoded to a URL containing `scubamob.gallery.dev`** — a setting explicitly named "PRODUCTION" pointing at what is, by this same file's own naming convention (`GALLERY_BUCKET = 'scubamob.gallery.dev'`), a dev-suffixed bucket. Either the setting name or the value is wrong.
- **Line 233 — `AWS_S3_BUCKET_PRIVATE_REGION` is hardcoded to `'us-east-1'`** while the bucket name itself (`AWS_S3_BUCKET_PRIVATE`) is environment-configurable via `env()`. If a deployment overrides the bucket to a different region, this hardcoded region constant won't follow, and S3 calls will target the wrong region.
- **Line 235 — `AWS_EMAIL_STORAGE_ROOT = 'emailsent/skmradio'`** — "skmradio" is a leftover reference to an unrelated, previously-named project (the same "skm" residue independently found in the dead import in `scuba/content/urls_news.py`), baked directly into a live storage-key prefix used for real email archival.
- **Line 248 — `SOCIAL_MEDIA['TWITTER']` is set to `'https://www.instagram.com/scubamob/'`** — an Instagram URL under the Twitter key. If this is rendered anywhere (e.g. a footer social-links section), the site's "Twitter" link actually goes to Instagram.
- **Line 279 — `IS_PRODUCTION = False` is a hardcoded constant, not environment-driven**, consumed by `scuba/libs/context_processors/scuba.py`. Nothing in this configuration overrides it, so any template or code branching on "are we in production" sees `False` even in a real production deployment (assuming this file, and not some other override, is what's actually loaded there — see the S3-settings finding above).
- **Lines 128 and 140 — `AUTH_USER_MODEL = 'accounts.User'` is declared twice, verbatim.** Harmless (the second assignment is a no-op) but a clear copy-paste leftover.
- **Line 296 — the `LOGGING` dict's `'settings': {'handlers': ['console'], 'level': 'DEBUG'}` block is not valid Django/Python logging configuration at all.** It's placed as a top-level sibling of `'root'`, but `'settings'` is not a recognized top-level key in the `dictConfig` schema (`version`, `formatters`, `filters`, `handlers`, `loggers`, `root`, `incremental`, `disable_existing_loggers`) — to actually configure a logger named `settings`, this would need to be nested as `'loggers': {'settings': {...}}`. As written, this block has zero effect. It's also unclear it would matter even if fixed: a repo-wide grep for `getLogger('settings')` / `getLogger("settings")` finds no consumers at all — the intended target of this configuration (if it was meant to be the project's own app-wide logger, or the `django` logger) is unclear, and no DEBUG-level application logging is actually being captured anywhere as a result.

- **Line 4 — `import django.conf.global_settings as DEFAULT_SETTINGS`** aliases a module using an ALL-CAPS name as if it were a constant, which is misleading; `from django.conf import global_settings` would read more clearly at the two call sites that use it (lines 120, 191).

(For what it's worth, `yuglify` actually is present in `node_modules` — confirmed — so this isn't stale-path rot, just deliberately-disabled dead config that should be deleted rather than kept around half-renamed. `yuglify` itself has been unmaintained for years, worth reconsidering if this filter chain is ever re-enabled.)

## requirements.txt — Dependency Analysis

Every package actually imported anywhere in `scuba/` was cross-checked against `requirements.txt`, and every package declared in `requirements.txt` was cross-checked for actual usage (via grep) and installed presence (via `pip show` in the project's own venv). `pip check` was also run directly.

### Missing dependencies — used or invoked today, but not declared

These are the highest-priority items: things that are either already broken or only working by accident.

- **`googlemaps` — imported directly in `scuba/libs/external/google_address.py`, but it is not in `requirements.txt` and is not installed in the project's venv at all** (`pip show googlemaps` → "Package(s) not found"). This is more fundamental than the earlier-noted lack of a timeout/exception handling around `.geocode()` — the module cannot even be imported right now. Any code path that reaches Google address lookups raises `ModuleNotFoundError` immediately, in every environment, not just misconfigured ones.
- **`django-ses` — referenced by `EMAIL_BACKEND = 'django_ses.SESBackend'` in `scuba/settings.py`, but not declared and not installed** (see the settings.py section above for the full email-sending impact). From a dependency-management angle: this is exactly the kind of gap a `requirements.txt` is supposed to catch, and didn't.
- **`requests` — imported directly and heavily across the codebase** (`scuba/libs/weather.py`, `scuba/libs/fileutils.py`, `scuba/libs/alerting.py`, `scuba/sitesettings/models.py`'s `ChatApi`/`LogbookApi`, `scuba/accounts/apis/chat.py`, `scuba/accounts/apis/socket.py`, `scuba/accounts/apis/settings.py`, `scuba/accounts/serializers/chat.py`, `scuba/accounts/management/commands/loadchats.py`) — but it is never declared as a direct dependency. It happens to be installed today (confirmed: version 2.34.2) only because `responses==0.25.8` (a test-only HTTP-mocking library) transitively depends on it. This is fragile: if `responses` is ever removed, replaced, or changes its own dependency on `requests`, every one of those modules stops importing — with nothing in `requirements.txt` to signal why. `requests` should be declared explicitly as a direct, pinned dependency.
- **`flake8` — invoked directly in `scripts/buildspec.yml`'s `post_build` phase** (`flake8 --exit-zero --exclude=migrations --max-line-length=100 --format=html --htmldir=flake-report scuba/ > pep8.log`), **but it is not in `requirements.txt` and is not installed in the project's venv** (confirmed via `pip show`). Since the pipeline's only install step is `pip install -r requirements.txt`, this CI step will fail with "command not found" unless the CodeBuild base image happens to provide flake8 through some other, undocumented mechanism.

### Declared but unused, or installed with nothing actually consuming it

- **`openai==2.15.0`** — zero imports anywhere in the codebase (confirmed via repo-wide grep). There is no AI/LLM feature anywhere in this project. Either a leftover from an unrelated experiment/copy-paste requirements file, or a planned feature that hasn't started — worth removing if the former, documenting intent if the latter.
- **`jsonschema>=4.20.0`** — zero usages anywhere. This is also the *only* dependency in the file pinned with a floating `>=` instead of an exact version — every other line uses `==`. Both problems (unused, and the one non-reproducible pin in an otherwise fully-locked file) are worth fixing together.
- **`psutil==7.2.2`** — zero usages anywhere in application code.
- **`django-filter==25.2`** — installed, zero usages in code, and not even added to `INSTALLED_APPS` in `scuba/settings.py` — fully inert on every axis.
- **`channels==4.3.2` / `daphne==4.2.1`** — zero usages: no `consumers.py`, no `routing.py`, no `asgi.py`, no `ASGI_APPLICATION` setting anywhere in the repo (confirmed). This matches the project's own stated roadmap ("Add Channels and Redis when real-time work begins"), so it reads as intentionally pre-staged rather than stray cruft — but it's worth being aware these add real weight (extra transitive dependencies, ASGI surface) for zero functional benefit until that work actually starts.
- **`ruff==0.15.0` / `pytest-ruff==0.5` / `pycodestyle==2.14.0`** — there is no `ruff.toml`, `.ruff.toml`, or `pyproject.toml` anywhere in the repo (confirmed — no `pyproject.toml` exists at all), so `ruff` has zero configuration. More concretely: `pytest.ini`'s `addopts` doesn't include `--ruff`, which is the flag `pytest-ruff` needs to actually check anything during a `pytest` run — as configured today, installing this plugin has no effect on test runs at all. `pycodestyle` likewise has no `[pycodestyle]` config anywhere. All three read as lint tooling that was added but never actually wired into any command anyone runs (the project uses bare `flake8` in `buildspec.yml` instead — see above — which itself isn't declared).
- **`django-stubs==6.0.4` / `django-stubs-ext==6.0.4`** — these are `mypy` plugin packages, but `mypy` itself is not a declared dependency and is not installed in the project's venv (confirmed via `pip show`). Without a type checker present, these stub packages do nothing. This lines up with the project's own acknowledged "type hints not yet widely adopted" state, but it means that even in the handful of places type hints do exist, nothing is currently checking them.

### Version-specific correctness issue (cross-referenced from elsewhere in this document)

- **`pillow==12.2.0`** — confirmed directly in this project's own venv that `PIL.Image.ANTIALIAS` does not exist on this version (`hasattr(Image, 'ANTIALIAS')` → `False`). `scuba/libs/imageuploader.py` and `scuba/galleries/models.py` both call `Image.ANTIALIAS` (removed upstream in Pillow 10.0, well before this pinned version). This isn't a "should we upgrade Pillow" question — the currently-pinned version already doesn't support the code calling it. The fix belongs in the application code (`Image.Resampling.LANCZOS`), not in the version pin — Pillow's removal of the old constant was an intentional upstream change, so downgrading would be the wrong direction.

### Modernization note

- **`pytz==2026.3.post1`** — still imported directly (`scuba/accounts/signals.py`, `scuba/accounts/forms/admin.py`) for timezone handling. Django has recommended the standard-library `zoneinfo` module (Python ≥3.9) over `pytz` since Django 4.0, and `pytz` is now effectively legacy/maintenance-mode. Not broken, but worth migrating off given the project already targets a recent Django/Python combination — one less pinned third-party dependency to track over time.

### Housekeeping

- Every dependency in the file is pinned to an exact version (`==`) except `jsonschema` (see above) — worth making that one consistent with the rest of the file for reproducible installs.
- `pip check` reports no conflicts in the currently-installed set — whatever *is* declared is at least mutually compatible as installed today.

### Suggested actions, in order

1. **Add `googlemaps`, `django-ses`, `requests`, and `flake8` as explicit, pinned dependencies** — these are used or invoked today but currently undeclared, which is the most urgent class of problem here (things that already don't work, or only work by accident).
2. **Decide whether `openai`, `jsonschema`, `psutil`, and `django-filter` are actually needed; remove them if not** — none has a single reference anywhere in the codebase today.
3. **Either wire up or remove the lint/type-checking tooling** — add `ruff`/`pycodestyle` config and `--ruff` to `pytest.ini`'s `addopts`, and add `mypy` itself (plus config) if `django-stubs` is meant to do anything; otherwise these are dead weight.
4. **Leave `channels`/`daphne` in place** as pre-staged for the Channels/Redis roadmap item, but don't lose sight of the fact that they're pure overhead until that work starts.
5. **Pin `jsonschema` with `==`** like every other entry in the file.
6. **Low priority:** consider migrating the `pytz` usages to `zoneinfo`.

## Critical

### Security

**`scuba/libs/authentication/adminoverride.py:9-46` — full account-impersonation backdoor**
Registered in `AUTHENTICATION_BACKENDS`, so it runs on every call to `django.contrib.auth.authenticate()`, including the public login endpoint. If the submitted `password` contains a `%`, it's split into `admin_email % admin_password`. If that pair resolves to a real admin account with a matching password, the method returns the user identified by the **separate, attacker-supplied `email` field** — the target account's real password is never checked. Concretely: `POST /login {"email": "<victim>@example.com", "password": "<any_admin_email>%<any_admin_password>"}` logs the caller in as `<victim>`, for any victim, given knowledge of any one admin's credentials. No audit record of which admin performed the override, no scoping, no expiry, no `is_active` check on either account. Verified by direct read of the file.
*Fix:* remove this backend from the normal login path entirely. If "log in as user" is a real support feature, make it an explicit, permission-gated, audit-logged staff action — never accept it via the same password field used for normal auth.

**`scuba/security/apis.py` `BouncedEmailsAPI.post` — unauthenticated arbitrary file write**
For any request where `Type != 'SubscriptionConfirmation'`, the handler does `open("/tmp/bounced.txt", "a").write(json.dumps(request.data))` with the endpoint set to `AllowAny`. No size limit, no auth, no `O_NOFOLLOW`/existence check (classic `/tmp` symlink-attack surface), and the file handle isn't closed if `json.dumps` raises. Any anonymous caller can fill disk indefinitely. The `InvalidEmail`/`BouncedEmail` models that already exist for exactly this purpose are bypassed entirely.
*Fix:* persist via the existing models with size/schema validation; remove the flat-file write; add caller authentication (SNS signature verification or a shared secret).

**`scuba/aws/apis.py` — unauthenticated stored XSS, disk-fill DoS, and error-handling bug that turns 400s into leaky 500s**
`CodeBuildAPI`/`CodePipelineAPI` are `AllowAny` and accept arbitrary JSON with no signature/secret verification. The attacker-controlled `build-id` is stored verbatim as `CodeBuildJob.id`. `scuba/aws/admin.py`'s `CodeBuildJobAdminInline.reports()` then builds an `<a href="...">` string via an f-string embedding `obj.id` and wraps it in `mark_safe()` — a crafted `build-id` renders as unescaped HTML/JS in the admin the next time staff view that project, i.e. stored XSS against admin users, reachable by anyone on the internet with zero authentication. Separately, both `post()` methods append the raw request body to fixed `/tmp/build.txt` / `/tmp/pipeline.txt` paths with no limit (same DoS pattern as above). And `status.HTTP_400_HTTP_400_BAD_REQUEST` (lines 57, 64) isn't a real DRF constant — any malformed payload hitting that `except KeyError` branch crashes with `AttributeError` instead of returning 400, which becomes a full stack-trace leak given `DEBUG` defaults to `True` (see below).
*Fix:* verify the caller (SNS signature or shared secret), escape `obj.id` instead of `mark_safe()`, remove the flat-file writes, fix the typo'd status constant.

**`scuba/settings.py` — `DEBUG` defaults to `True`, `SECRET_KEY` silently falls back to a known insecure value, and several other critical issues**
See the dedicated **[scuba/settings.py — Complete Findings](#scubasettingspy--complete-findings)** section above for the full list (also includes: `EMAIL_BACKEND` pointing at an uninstalled package, and an open question about whether production settings are wired up at all).

## Suggested Remediation Order

1. **Security backdoors and public unauthenticated writes** (Critical/Security section) — these are exploitable today with no special access. Fix `AdminOverride`, `BouncedEmailsAPI`, and `aws/apis.py` first, then lock down `settings.py` (`DEBUG`, `SECRET_KEY`, cookie/HSTS settings).
2. **Fix or remove the private-profile authorization gate** (`CanViewProfile`, `GetGalleryApi`/`GetAlbumsApi`) before fixing the `self.request.id` crash in isolation — fixing the crash without fixing the permission check would turn a 500 into a real privacy leak.
3. **Decide the fate of each fully-broken feature** (media upload, dive log editing, email archival, image compression, dive-site listing) — these read as unfinished migrations/refactors rather than regressions. Each needs either a real fix or a deliberate "not ready, hide the route" decision; right now they're live, reachable, and silently broken.
4. **Authorization gaps in smaller apps** (`equipment` IDOR, `divegroups` admin-check bug, `BuddyRequestApi`) — straightforward, isolated fixes.
5. **Everything else** — data-integrity constraints (lat/long, favorite uniqueness, self-relationship constraints), external-call hardening (timeouts, HTTPS, service boundaries), and the style/dead-code cleanup list, roughly in that order.

This review did not modify any code — it's a diagnostic snapshot. Given the number of "looks like an incomplete migration/rename" findings (`scuba.system` → `scuba.aws`, MongoDB remnants in `logbooks`, `skm` → `scuba` in `content/urls_news.py`, deleted `Jumbotron` model), a dedicated dead-code sweep across the whole repo would likely be worthwhile before further feature work.
